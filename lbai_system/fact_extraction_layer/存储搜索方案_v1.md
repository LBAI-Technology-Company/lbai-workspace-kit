# 事实抽取层存储搜索方案 v1

本文档说明：文档转成 JSON 后，应该如何存储、搜索、查询最新结论，以及 AI 和 Python 各自负责什么。

你的理解是对的：

```text
文档转成 JSON 的价值：
1. 方便 AI 理解
2. 方便 Python 使用
3. 方便搜索
```

但更准确地说：

```text
原始文档适合人读。
结构化 JSON 适合 AI 继续理解、Python 稳定判断、系统长期搜索。
```

## 一、为什么要把文档转成 JSON

### 1. 方便 AI 理解

原始会议纪要、需求文档、客户反馈往往是长文本，里面混合了背景、讨论、决定、问题、行动项。

AI 每次直接读原文，会有几个问题：

```text
容易遗漏细节
容易把讨论当结论
容易把旧决定当最新决定
容易混淆不同功能、不同阶段、不同来源
```

转成 JSON 后，AI 看到的是更稳定的结构：

```json
{
  "subject": {
    "type": "feature",
    "id": "feature.team_permissions",
    "name": "团队权限管理"
  },
  "entity": {
    "type": "decision",
    "id": "dec_custom_roles_v1"
  },
  "value": "v1_no_custom_roles",
  "status": "confirmed",
  "evidence_text": "最终确认第一版不支持自定义角色"
}
```

这样 AI 后续总结、生成 PRD、发现冲突时，不需要重新从长文本里猜。

### 2. 方便 Python 使用

Python 不擅长理解自然语言，但非常擅长处理字段、枚举、时间、状态和关系。

例如 Python 可以稳定判断：

```text
status 是否等于 confirmed
source_occurred_at 哪条更新
entity.type 是否是 decision
action_item 是否还 open
field_id 是否匹配 decision.scope
```

所以系统设计应该是：

```text
AI 把自然语言变成结构化 JSON
Python 根据 JSON 做确定性判断
```

不要让 Python 去理解“这句话到底是不是最终决定”；应该让 AI 先抽取：

```json
{
  "status": "confirmed"
}
```

然后 Python 只判断：

```text
status == confirmed
```

### 3. 方便搜索

原始文档只能做全文搜索，容易搜到一堆无关上下文。

JSON 化以后，可以按结构搜索：

```text
查某个功能的所有决策
查所有 open 的问题
查某个人负责的行动项
查某个字段当前最新确认值
查某个结论的历史变化
查某个材料来源支持了什么结论
```

这比单纯关键词搜索稳定得多。

## 二、存储不要覆盖，要追加事件

不同来源的信息可能在不同时间反复提到同一件事。

例如：

```text
6 月 1 日会议：第一版可能支持自定义角色
6 月 3 日 PRD：建议第一版不支持自定义角色
6 月 8 日决策记录：最终确认第一版不支持自定义角色
```

如果只保存“最新 JSON”，旧信息会被覆盖，证据链会丢失。

推荐做法是：

```text
每次文档抽取后，都追加为 fact_event 事件。
查询时再计算当前有效结论。
```

也就是：

```text
原始文档
  ↓
事实抽取 JSON
  ↓
fact_event 事件
  ↓
事件库 JSONL / SQLite
  ↓
查询当前结论或历史脉络
```

## 三、推荐存储结构

第一版推荐用文件系统 + JSONL，透明、简单、方便调试。

```text
knowledge_store/
  sources/
    meetings/
      mtg_20260608_product_review/
        raw.md
        extracted.json
        events.jsonl
    prds/
      prd_team_permissions/
        raw.md
        extracted.json
        events.jsonl
  indexes/
    fact_events.jsonl
```

其中最关键的是：

```text
indexes/fact_events.jsonl
```

每一行是一条事实事件。

## 四、事实事件字段设计

一条事实事件至少应该包含：

```json
{
  "schema_version": "fact_event_v1",
  "event_id": "evt_20260608_001",
  "subject": {
    "type": "feature",
    "id": "feature.team_permissions",
    "name": "团队权限管理"
  },
  "entity": {
    "type": "decision",
    "id": "dec_custom_roles_v1"
  },
  "field_id": "decision.scope",
  "value": "v1_no_custom_roles",
  "status": "confirmed",
  "validity": {
    "source_occurred_at": "2026-06-08",
    "recorded_at": "2026-06-08T10:00:00+08:00",
    "extracted_at": "2026-06-08T10:30:00+08:00"
  },
  "source": {
    "type": "official_decision_log",
    "id": "decision_log_20260608",
    "path": "decisions/2026-06-08-team-permissions.md",
    "priority": 80
  },
  "evidence_text": "最终确认第一版不支持自定义角色，只保留 owner/admin/member。",
  "supersedes": ["evt_20260601_001", "evt_20260603_001"],
  "related_to": ["req_team_permissions_roles"],
  "confidence": 0.96
}
```

核心字段含义：

```text
subject：这条事实属于哪个业务对象，例如某个功能、项目、客户、合同。
entity：这条事实是什么实体，例如 decision、requirement、action_item、risk。
field_id：这条事实描述哪个字段。
value：字段值。
status：状态，例如 proposed、confirmed、open、closed。
validity：时间信息。
source：来源信息。
evidence_text：证据原文。
supersedes：这条记录覆盖了哪些旧记录。
related_to：关联的需求、问题、决策或行动项。
```

## 五、如何搜索

推荐采用混合搜索：

```text
关键词搜索
+ 同义词 / 概念词典搜索
+ 向量搜索
+ Python 结构化过滤
```

其中：

```text
关键词搜索：解决明确词命中。
同义词 / 概念词典：解决买车、购车、提车这类同一概念的不同说法。
向量搜索：解决主题相似但字面不一致的问题。
Python 结构化过滤：解决哪些事实有效、最新、可信。
```

### 1. 查当前最新确认结论

适合问题：

```text
团队权限管理第一版到底支不支持自定义角色？
这个功能最终决定是什么？
当前确认的范围是什么？
```

查询条件：

```text
subject.id = feature.team_permissions
entity.type = decision
field_id = decision.scope
status = confirmed
mode = current
```

Python 会按规则取一条当前有效结论。

### 2. 查历史脉络

适合问题：

```text
这个决定是怎么变成现在这样的？
之前有没有不同说法？
哪些会议或文档影响了这个决定？
```

查询条件：

```text
subject.id = feature.team_permissions
entity.id = dec_custom_roles_v1
mode = history
```

返回从旧到新的完整变化链。

### 3. 查待处理事项

适合问题：

```text
还有哪些 open action item？
Alice 还有哪些未完成事项？
这个功能还有哪些 open question？
```

查询条件：

```text
entity.type = action_item
status = open
mode = list
```

### 4. 查语义相关内容

适合问题：

```text
之前有没有讨论过类似自定义权限的东西？
客户权限相关的争议有哪些？
为什么第一版不做某个能力？
```

这类问题可以先用 AI 生成查询计划，再用向量搜索找候选材料，最后用结构化 fact_event 做最终确认。

推荐流程：

```text
新任务
  ↓
AI 生成查询意图、关键词、概念候选
  ↓
关键词 / 同义词 / 向量搜索召回候选事件
  ↓
Python 按 subject/entity/status/time/source_priority 过滤
  ↓
返回可追溯证据
```

例如新任务是：

```text
整理提车前要准备什么
```

历史材料里可能写的是：

```text
车辆交付前需要确认保险、上牌、付款凭证和经办人身份证明。
```

关键词搜索可能搜不到“提车”，但向量搜索可以找到“车辆交付前准备”这个主题相关内容。

然后 Python 再判断：

```text
status 是否 confirmed
source_occurred_at 是否最新
source.priority 是否足够高
是否已被 superseded
```

所以：

```text
向量搜索解决“主题在哪里”。
Python 解决“哪些事实有效”。
AI 解决“如何理解和使用这些证据”。
```

## 六、向量搜索在系统中的位置

向量搜索适合放在搜索流程的第一步或第二步，用来扩大候选范围。

推荐流程：

```text
新任务输入
  ↓
AI 生成查询计划
  ↓
向量搜索召回主题相关事件 / 文档片段
  ↓
关键词和概念词典补充召回
  ↓
Python 按字段过滤、排序、去重、裁决
  ↓
生成证据包
  ↓
AI 阅读证据包并执行任务
```

### 向量搜索主要解决什么

向量搜索主要解决“主题相关性”。

例如：

```text
买车
购车
提车
车辆采购
车辆交付
公司用车
商务车
上牌
保险
```

这些词不完全相同，但在公司资料里可能都属于：

```text
company_vehicle_purchase
```

向量搜索可以帮助系统在没有完全命中关键词时，找到语义相近的材料。

### 向量搜索不负责什么

向量搜索不应该负责最终裁决。

它不适合判断：

```text
哪个是最新决定
哪个是 confirmed
哪个来源优先级更高
哪个行动项还 open
哪个结论已经被 superseded
哪些记录互相冲突
```

这些必须由 Python 根据结构化字段判断。

### 向量搜索的输入

可以向量化这些内容：

```text
原文片段 raw chunk
fact_event.evidence_text
fact_event.value
subject.name
entity.type
field_id
概念词 aliases
```

推荐每个向量条目都保留指向 fact_event 的 ID：

```json
{
  "vector_id": "vec_evt_20260608_001",
  "event_id": "evt_20260608_001",
  "text": "最终确认第一版不支持自定义角色，只保留 owner/admin/member。",
  "subject_id": "feature.team_permissions",
  "entity_type": "decision",
  "status": "confirmed"
}
```

这样向量搜索只负责返回候选 `event_id`，后续由 Python 读取完整事件并做结构化过滤。

### 向量搜索后的 Python 过滤

向量搜索返回候选后，Python 继续做：

```text
按 subject/entity/field_id 过滤
按 status 过滤
按 source_occurred_at 排序
按 source.priority 排序
排除 rejected/superseded
检测同优先级冲突
返回证据包
```

因此整个系统不是“向量搜索说了算”，而是：

```text
向量搜索召回候选。
Python 判断有效事实。
AI 使用证据完成任务。
```

## 七、最新结论如何裁决

默认排序规则：

```text
1. 排除 rejected / superseded
2. 优先 confirmed
3. source_occurred_at 最新
4. recorded_at 最新
5. source.priority 最高
6. confidence 最高
```

如果同等优先级出现不同值：

```text
返回 conflict，不自动选择。
```

例如：

```text
同一天两条 confirmed 决策互相矛盾
来源优先级一样
时间一样
value 不同
```

这时必须进入人工确认。

## 八、AI、向量搜索和 Python 的分工

### AI 负责

```text
读原始文档
抽取实体
识别讨论、决定、问题、行动项、风险
把自然语言转成 JSON 字段
标注 evidence_text
发现 unmapped_facts
提出字段变更建议
为新任务生成查询意图、关键词和概念候选
```

### 向量搜索负责

```text
主题召回
语义相似匹配
发现字面不一致但含义相关的材料
返回候选 event_id 或文档片段
```

### Python 负责

```text
校验 JSON 格式
校验字段是否注册
校验枚举和类型
按时间和状态搜索
按来源优先级排序
判断是否存在冲突
返回当前有效事实
回放历史测试
对向量搜索结果做结构化过滤
```

一句话：

```text
AI 负责理解和结构化。
向量搜索负责主题召回。
Python 负责校验、字段过滤、搜索和裁决。
```

## 九、为什么这套方案适合多材料工作

因为一个工作不会只依赖一份材料。

真实工作通常是：

```text
会议记录给出讨论过程
PRD 给出阶段性方案
决策记录给出最终结论
任务系统给出执行状态
客户反馈给出外部约束
人工确认给出最高优先级修正
```

把它们都转成 fact_event 后，系统可以问：

```text
当前确认结论是什么？
这个结论来自哪里？
有哪些旧说法被覆盖？
还有哪些 open 问题？
哪些行动项没有关闭？
哪些材料之间冲突？
```

这才是后续 Agent 能稳定工作的基础。

## 十、第一版实现建议

第一版不需要复杂数据库。

推荐：

```text
raw.md：保存原文
extracted.json：保存事实抽取结果
events.jsonl：保存该文档产生的事实事件
indexes/fact_events.jsonl：汇总所有事实事件
query_fact_events.py：执行结构化查询
```

数据量变大后，再升级：

```text
SQLite / DuckDB：结构化查询
全文搜索：关键词检索
向量库：语义检索
图数据库：复杂关系追踪
```

但第一版最重要的是：

```text
先把事实事件结构稳定下来。
```
